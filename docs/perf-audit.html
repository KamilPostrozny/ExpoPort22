MEDIUM

N name-pill BlurViews stay composited at opacity 0 for the whole session

src/keybar.tsx:830 Gestures & chrome

What the code does

<View style={[styles.namesWrap, !props.pills.live && { opacity: 0 }]}> (line 830) mounts one NamePill per tmux window whenever props.pills != null — i.e. from the moment tabs are reachable, for the entire session, not just during a swipe. Each NamePill renders Glass (line 969), which on iOS is a BlurView intensity={40} (line 255). So N UIVisualEffectViews sit stacked in the key-bar slot sampling their backdrop every frame while the user types and the terminal streams. This repo already established on device that this is not free: terminal.tsx:2053-2056 says "a UIVisualEffectView re-renders its backdrop continuously and does NOT stop costing GPU because a parent's opacity is zero" — the lesson was applied to the grid blur and missed here. The same applies inverted to line 782, where the keys' own glass stays composited under opacity: 0 for the whole swipe.

Change

Swap opacity: 0 for display: 'none' on both the namesWrap (line 830) and the keys wrapper (line 782). The views stay allocated, so the pre-mount that this code exists to guarantee (no BlurView construction on the swipe's first frame) is preserved, but a hidden view is not composited.

Verifier's check

Confirmed on both ends. keybar.tsx:830 is style={[styles.namesWrap, !props.pills.live && { opacity: 0 }]} guarded only by props.pills != null && pillW > 0 (826), and terminal.tsx:1714-1727 makes pillsProp non-null for showTabs && connected && stage !== null — i.e. the whole tmux session. Each NamePill renders <Glass …> (968) whose iOS branch is <BlurView intensity={40} …/> (255). The repo has already established the cost class on device twice in its own words: terminal.tsx:2053 "a UIVisualEffectView re-renders its backdrop continuously and does NOT stop costing GPU because a parent's opacity is zero" and switcher.tsx:305-307 repeats it. styles.namesWrap is { position: 'absolute', left: 0, right: 0, top: 0, bottom: 0 } (1217) and the pills are StyleSheet.absoluteFill, so flipping to display: 'none' costs a trivial re-layout on the swipe's first frame and keeps the native views allocated. Downgraded from high: the pills stack in one small centred slot, not the full screen that produced the measured lag.

Reanimated/Expo per-frame cost budget: keep concurrently compositing/animating layers to what the frame can pay for; a hidden-but-composited backdrop blur is pure waste. docs.swmansion.com/react-native-reanimated/docs/guides/performance

One DOM-bridge injectJavaScript per SSH chunk, no coalescing

src/session.ts:219 SSH → screen path

What the code does

emit() calls sink?.(base64) for every onShellData event, and the sink (src/app/terminal.tsx:422) calls terminal.current?.write(base64) immediately. The native Swift side emits one event per channel read (modules/expo-ssh/ios/ExpoSSHModule.swift:51, for await chunk in stream), so there is one bridge crossing per PTY read. Each crossing is not a cheap JSON post: expo/dom's proxy (node_modules/expo/src/dom/webview-wrapper.tsx:55-57) does JSON.stringify(arg) and then webviewRef.current?.injectJavaScript("window._domRefProxy.write(...)") — so every chunk becomes a JavaScript *source string* containing the whole base64 payload, dispatched to WKWebView's main thread as an evaluateJavaScript, then parsed by JSC before write even runs. The file's own comment at src/app/terminal.tsx:419 records the measured shape: "a tmux redraw after a switch is hundreds of chunks" — hundreds of main-thread evaluateJavaScript hops and hundreds of source parses, landing exactly during the switch animation.

Change

Buffer in emit: push to a pending array and flush once per frame (requestAnimationFrame/setTimeout 0) through a sink typed (chunks: string[]) => void; widen TerminalHandle.write (src/terminal.tsx:52) to write(chunks: string[]) and loop term.write(fromBase64(c)) inside the webview. Do not string-concat the base64 — each chunk is independently padded.

Verifier's check

Mechanism confirmed end to end. src/session.ts:219 sink?.(base64); with no buffering; the sink at src/app/terminal.tsx is terminal.current?.write(base64); where terminal is the expo/dom proxy — node_modules/expo/src/dom/webview-wrapper.tsx:55-57 const serializedArgs = args.map((arg) => JSON.stringify(arg)).join(','); webviewRef.current?.injectJavaScript(\window._domRefProxy.${propName}(${serializedArgs})\), and the native end is node_modules/@expo/dom-webview/ios/DomWebView.swift:195-197 DispatchQueue.main.async { self?.webView?.evaluateJavaScript(script) } — one main-thread hop plus a full JS source parse per chunk. Native emits per channel read (ExpoSSHModule.swift for await chunk in stream { self?.sendEvent("onShellData", …) }), and the in-repo comment at the sink says 'a tmux redraw after a switch is hundreds of chunks'. Downgraded from high: each hop is an async main-thread IPC of a few KB (tens of µs), so a redraw burst costs milliseconds spread over the animation, not a freeze. The fix is small and correct; the severity is not high.

Never make one native→DOM write() call per SSH chunk — buffer chunks natively and flush at most once per frame in a single call docs.expo.dev/guides/dom-components

Card drag reads two shared values from the JS thread on every frame

src/switcher.tsx:791 Gestures & chrome

What the code does

The reorder pan is .runOnJS(true) (line 773) — defensibly so, since targetSlot runs against React state — but onUpdate then does live.current.onDragMove(x.value, y.value) (line 791) immediately after writing them (lines 789-790). Compute once and reuse: const nx = base.current.x + e.translationX, ny = base.current.y + e.translationY; x.value = nx; y.value = ny; live.current.onDragMove(nx, ny);. Identical semantics, zero reads.

Expo 14

  1. With experiments.reactCompiler enabled, do not add new useMemo/useCallback/React.memo for render-cost reasons; keep them only where a value is an effect dependency or feeds a non-React consumer, and never ship a "use no memo" directive without a comment saying why.

  2. Call SplashScreen.preventAutoHideAsync() at module scope (never inside a component or effect, never awaited) and gate hideAsync() only on genuinely blocking resources — fonts, restored session — not on network fetches or non-critical state.

    Called from a component/effect it can run too late to take effect at all. Every millisecond the splash stays up is added to cold launch; Expo's target is cold launch under 1.5s and Time to First Render under 2s including launch.

    Spot it grep preventAutoHideAsync — it must be a bare top-level statement in the entry/root layout file, not inside a function body, and not preceded by await; then grep hideAsync and check what is awaited before it

  3. Keep module top-level scope free of work: no synchronous storage/filesystem reads, no top-level await, no heavy table/regex/theme generation at import time.

    Bundle load time (JS evaluation) has an Expo-published target of under 0.3s, and every top-level statement in every reachable module is on that path. Blocking or synchronous I/O in top-level scope is the specific cause Expo names for slow Time to First Render.

    Spot it in each module, look at statements outside any function/component: await at top level, SecureStore.*, AsyncStorage.*, FileSystem.*, .getItemSync, and non-trivial loops or Object.entries(...).map(...) building constants

  4. Split heavy screens with React.lazy and keep imports ESM — no require() / module.exports in app code, and no barrel index.ts files that export * for convenience.

    Tree shaking is on by default from SDK 54 and works only on ESM syntax; CommonJS is never shaken, and a barrel file pulls the whole re-exported graph into evaluation. React.lazy on screen-level components is the documented way to keep large components off the startup path.

    Spot it grep require( and module.exports in src/; grep export * from and any src/**/index.ts that only re-exports; check that big screens are React.lazy(() => import(...)) rather than statically imported into the root layout

  5. Use expo-image's <Image>, not react-native's; set cachePolicy explicitly, and pass recyclingKey for any image rendered inside a recycling list.

    Without recyclingKey a recycled row shows the previous row's image until the new one decodes (visible flicker); recyclingKey resets the view to blank/placeholder first. allowDownscaling (default true) is what keeps decoded bitmaps at container size rather than source size — turning it off raises memory materially.

    Spot it grep Image imported from 'react-native'; grep <Image inside a renderItem/list row and check for recyclingKey; grep allowDownscaling={false} and cachePolicy= presence

The webview also runs plain JavaScript, not Hermes bytecode, so its parse and startup cost is higher than the native side.

    Spot it grep files containing 'use dom'; at each call site check the props for inline object/array literals, high-frequency state (terminal output buffers, scroll offsets) and function-valued props other than the async action pattern

React 6

  1. Delete every hand-written useMemo / useCallback / React.memo unless you can name the reason it survives — with the compiler on, it is dead weight that also constrains the compiler.

    The compiler applies "the equivalent of manual memoization" automatically and more granularly than you can (it memoizes conditionally and after early returns, which useMemo cannot). react.dev states outright: "You can safely remove React.memo from your components when using React Compiler." Worse than useless: the compiler *preserves* your existing useMemo/useCallback/memo calls, and it only compiles a function when its inference "matches or exceeds the existing manual memoization" — so a hand-memo with an incomplete dep array can hold the whole function back. Meta's Quest Store measured 12% faster initial loads/navigation and 2.5x faster interactions after enabling it.

    Spot it grep -rn 'useMemo(\|useCallback(\|React\.memo(\|\bmemo(' src/ --include='*.tsx' --include='*.ts'. In this repo that hits src/keybar.tsx, src/switcher.tsx, src/app/terminal.tsx. For each hit ask: is the memoized value crossing into a non-React consumer (a worklet, an imperative xterm/SSH call, a native @expo/ui prop)? If not, delete it. Then run eslint with react-hooks/preserve-manual-memoization enabled and fix anything it flags rather than leaving a half-memoized dep array.

    On this stack Current for React 19.2 + compiler 1.0. The compiler does NOT require React 19 (17+ works with react-compiler-runtime), but on 19.2 no runtime shim is needed. Advice from 2024 blog posts telling you to add memo everywhere for RN is obsolete on this stack.

    react.dev/reference/react/memo

  2. Never read or write ref.current in a render body — move it into an effect, an event handler, or a worklet.

    Refs are not initialized during render and their values can be stale or inconsistent; because they don't trigger re-renders, reading them in render breaks React's model and the compiler's assumptions. The refs lint flags it, and it is one of the classic causes of a silent bailout for the enclosing function — which, per guideline 3, means the entire screen loses memoization.

    Spot it grep -n 'Ref\.current\|ref\.current' src/**/*.tsx and for each hit check the enclosing scope: inside useEffect, a on* handler, or a callback = fine; directly in the component body or inside a JSX expression = violation. The lint also catches identifiers merely *named* ref/*Ref accessing .current, and refs passed through JSX ref props, so enable react-hooks/refs rather than grepping alone.

    On this stack eslint-plugin-react-hooks v6, included by default on Expo SDK 55+. React 19 removed the need for forwardRef (ref is a normal prop), which makes it easier to accidentally thread a ref somewhere it gets read during render.

    react.dev/reference/eslint-plugin-react-hooks/lints/refs

  3. Split contexts by update frequency and keep high-frequency values out of context entirely — the compiler memoizes the value object but cannot stop a changed value from re-rendering every consumer.

    This is the largest gap between what people assume the compiler does and what it does. The compiler will memoize the { a, b, c } object you pass as value, so you no longer need the useMemo — but the moment any one field changes, the object identity changes and *every* consumer re-renders regardless of which field it reads. React's own memo docs are explicit: "Even when a component is memoized, it will still re-render when a context that it's using changes." So a single theme+session+layout context updated on every keystroke fans out across the whole screen. Two fixes, both cheap: separate providers per update cadence, and pass children through so the provider's own re-render doesn't re-render the subtree.

    Spot it grep -rn 'createContext' src/ then for each: count fields in the value object and grep -rn 'useContext(<Name>)' src/ | wc -l. Flag any context whose value mixes a value that changes per frame/keystroke with values that change rarely. Secondary tell: a provider component that holds useState AND renders the subtree inline instead of {children}.

    On this stack React 19 lets you render <Context value={...}> directly (no .Provider) — cosmetic, changes nothing about fan-out. The compiler's context handling is unchanged in 1.0; no version of it splits contexts for you.

    react.dev/reference/react/useContext

  4. Bridge non-React state (tmux model, session/SSH state, xterm buffer) into components with useSyncExternalStore, with subscribe defined at module scope and getSnapshot returning a cached value.

    Mirroring an external store into useState via useEffect gives you an extra render per change and a tearing window; useSyncExternalStore is the supported path and lets each component subscribe to exactly the slice it needs (component-level fan-in instead of context fan-out). Two pitfalls that bite immediately: getSnapshot "must return an immutable snapshot" and repeated calls must be Object.is-equal or you get an infinite render loop; and subscribe defined inside the component body resubscribes on every render — hoist it to module scope or wrap in useCallback. The compiler does not fix either: it "only memoizes React components and hooks, not every function", and module-level state is entirely outside its model.

    Spot it grep -rn -B3 -A8 'useEffect' src/*model*.ts src/session.ts src/tmux*.ts looking for the shape useState(store.get()) + useEffect(() => store.subscribe(setX)) — that is a useSyncExternalStore in disguise.     On this stack Stable since React 18, unchanged in 19.2. On this stack getServerSnapshot is irrelevant (no SSR in the native app), and Expo's compiler integration is "disabled for server rendering scenarios" anyway.

    react.dev/reference/react/useSyncExternalStore

  5. Replace {open && <Sheet/>} mount/unmount toggles for heavy panels with <Activity mode={open ? 'visible' : 'hidden'}>.

    React 19.2's Activity hides children, unmounts effects, and "defers updates until React has no other work" — so the hidden subtree keeps its state but stops competing for the JS thread, and pre-rendering the next panel makes opening it feel instant. For a settings sheet / switcher / upload sheet that currently pays a full mount cost each open (and loses scroll position and input state each close), this is a bigger win than any memoization.     Spot it grep -rn '&& <[A-Z]' src/app/terminal.tsx src/*.tsx for conditional mounts of non-trivial subtrees (sheets, switcher, popovers), and cross-reference with state that exists in the parent only to be preserved across close/open (settingsOpen, sw, rbOpen, pendingUpload are that shape here).

    On this stack New in React 19.2 (this stack is on react 19.2.3, so it is available). Verify behaviour on device rather than assuming — Activity's React Native support is not called out in the release post, so treat it as measure-before-adopt rather than a safe blanket change.

    react.dev/blog/2025/10/01/react-19-2

  6. Audit for libraries with "interior mutability" APIs — the compiler detects some and silently skips memoization for the component, and misses others entirely.

    React's incompatible-library lint ships a known list including react-hook-form's watch() and TanStack Table's useReactTable(); MobX's observer() is incompatible but "not yet detected by the linter".     On this stack eslint-plugin-react-hooks v6 / compiler 1.0. The detection list grows over release to release, so re-run lint after upgrading rather than trusting a one-time audit.

  1. Implement xterm.js flow control: pass the write() callback and pause the SSH channel above a high watermark (HIGH ≤ 500 KB), resuming below a low one.

    xterm parses at "5 - 35 MB/s"; a faster producer grows the input buffer unboundedly to a hardcoded 50 MB cap after which "data gets discarded", with UI sluggishness and unresponsive keystrokes on the way there.   1. With FlashList v2, keep list props memoized (or in a compiled component), never put a key on the item component or its children, use getItemType, and use useRecyclingState instead of useState inside items.

  2. Never assume a component compiled — wire babel-plugin-react-compiler's logger into babel.config.js and fail/report on CompileSkip and CompileError, because bailouts are silent by design.

    The compiler "safely skips optimization rather than risk changing your app's behavior" and emits unoptimised code with no build warning. On a screen you *believed* was memoized, that is an invisible performance regression that only shows up as dropped frames. The plugin's LoggerEvent union is CompileSuccessEvent | CompileErrorEvent | CompileDiagnosticEvent | CompileSkipEvent | CompileUnexpectedThrowEvent | PipelineErrorEvent | TimingEvent; CompileSuccess also carries memo-slot metrics, so you get per-function proof plus a rough measure of how much memoization was installed.     Spot it In babel.config.js, configure the plugin explicitly (babel-preset-expo auto-adds it from experiments.reactCompiler, so you must pass options yourself) with logger: { logEvent(filename, event) { if (event.kind !== 'CompileSuccess') fs.appendFileSync('/tmp/rc.log', filename + ' ' + event.kind + ' ' + (event.fnLoc?.start.line ?? '') + '\n'); } }. Then npx expo start --clear (or expo export) and read /tmp/rc.log. Cross-check individual components with the ✨ badge in React DevTools.     On this stack react-compiler-healthcheck is being deprecated and pulled from the docs (it encouraged the wrong idea that 100% compilation is a prerequisite) — do not build a CI gate on it.   3. Split any component whose body exceeds a few hundred lines — the compiler's optimization granularity is the whole function, so one rules-of-React violation anywhere in a 2700-line screen de-optimizes all 2700 lines at once.

    This is the real answer to "is size itself the problem": size alone is not, but size multiplies the blast radius of a bailout and of every state update. The compiler "only looks at the code inside of a component or hook body" and skips over the whole component or hook when it can't prove safety. In this repo SessionScreen (src/app/terminal.tsx:123–1991) is one ~1870-line function: a single ref.current read or an unrecognised mutation buried at line 1600 costs you memoization for the entire screen and every JSX subtree it builds. Bailouts here are also known to be under-reported — a plain try/catch/finally in a component body has silenced all compiler lint errors for that component (facebook/react#35644). Independently of the compiler, React "will call the function component whose state update triggered the render" — the whole body re-executes on every one of the screen's 20 setStates.

    Spot it find src -name '*.tsx' | xargs wc -l | sort -rn | head and flag anything over ~400 lines. For each, awk 'NR>=START && NR<=END' file | grep -c 'useState' — 20 useState in one body (as here) is the signal.     On this stack Compiler 1.0 / infer mode. Note the flip side: with the compiler ON and no bailout, a large component is much cheaper than it used to be, because the compiler memoizes intermediate values and JSX subtrees within the function. So the fix priority is (1) prove it compiled, (2) colocate state, (3) only then split for size.

Essays 1

  1. Colocate state with the smallest subtree that reads it — every setState at the top of a big screen re-runs that entire component function and recursively renders everything under it.

    React "will call the function component whose state update triggered the render" and the process "is recursive" down the tree. The compiler blunts the *child* cost (unchanged JSX subtrees are reused) but never the *parent* cost: the 1870-line body runs top to bottom every time. In this repo setSearch, setOcc, setRbOpen, setPageSwipe etc. all live in SessionScreen, so a search keystroke re-executes the keybar, ribbon, switcher and status logic. Moving state down means React skips the unaffected components entirely instead of re-running and diffing them.

    Spot it For each useState in a large component, grep its setter and getter names within the file: if all reads are confined to one JSX subtree, that state belongs in that subtree's component. grep -n 'setSearch\|setOcc\|setRbOpen' src/app/terminal.tsx is the shape of the check. React DevTools Profiler "Highlight updates when components render" confirms the fan-out before and after.

    On this stack Timeless, and *more* valuable with the compiler on, not less: the compiler cannot move state, and colocation is the only fix for the parent-body re-execution cost. React 19.2's Performance Tracks (Scheduler + Components tracks) give you a timeline view of this in DevTools.
